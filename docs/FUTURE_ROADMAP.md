# Jellyfish Climb 将来構想・段階的ロードマップ

更新日: 2026-08-01
ステータス: 検討資料（実装確定ではない）

## 1. この資料の目的

Jellyfish Climb を一度に大きく作り変えず、現在のゲーム性や操作感を確認しながら段階的に発展させるための構想をまとめる。

個人制作として無理なく楽しめる範囲を大切にしつつ、プレイヤーが増えた場合には継続的なアップデートやビジネス展開も検討できる状態を目指す。

## 2. 開発の基本方針

- 現在の Time Attack をゲームの基準として安定させる
- 一度のアップデートで追加する主要要素は原則1つに絞る
- 新要素は、追加する目的とゲーム内での役割を決めてから実装する
- PCとスマートフォンの得点条件が大きく変わらないよう調整する
- スキンによって当たり判定や性能を変えない
- プレイ中には広告を表示しない
- 実際のプレイ結果と反応を見て、次の更新内容を決める

## 3. 現在のゲームの中心

現在の中心となる遊びは、次の要素で構成されている。

- 拍動するタイミングを見極めて上昇する
- クラゲの向きを調整して横方向へ移動する
- 水流を利用または回避する
- プランクトンを集める
- 制限時間内にゴールする
- プランクトン得点へ残り時間の Time Rate を掛けて最終得点を競う

将来の機能は、この中心となる操作と判断を活かせるものを優先する。

## 4. 将来展開の3本柱

### 4.1 プランクトンの種類

プランクトンを、得点源だけでなくルート選択や操作判断を生む要素へ発展させる。

| 仮称 | 動き・効果 | 得点案 | ゲーム内での役割 |
| --- | --- | ---: | --- |
| Normal | 現在と同じ動き | 100 | 基本の得点源 |
| Swift | 横方向へ素早く泳ぐ | 200 | 操作精度を試す |
| Evasive | クラゲが近づくと逃げる | 300 | 追いかける判断を生む |
| Jet | 取得時の向きへ短時間ブースト | 0〜50 | 移動・立て直し・ショートカット |
| Haste | 一定時間、拍動による移動を強化 | 未定 | 一時的な速度上昇 |
| Float | 一定時間、重力による沈下を軽減 | 未定 | ミスからの回復 |

#### 追加時の注意点

- 最初は Normal に加えて1種類だけ追加する
- 色だけでなく、形・発光・動きでも種類を区別する
- スマートフォンでも取得可能な速度と逃走距離にする
- 高得点プランクトンを取る危険と、ゴールを急ぐ価値を両立させる
- Time Attack では移動補助そのものが Time Rate を高めるため、ブースト系へ高得点を付けすぎない
- プランクトン数をデバイスごとに変えて、最高得点に差が出る設計は避ける

### 4.2 Endless モード

ゴールをなくし、可能な限り高く上昇し続ける別モードとして検討する。

単に制限時間とゴールを取り除くだけでは緊張感がなくなるため、目的・終了条件・難易度上昇をセットで設計する。

#### 推奨する基本案

- 下方から深海の暗闇、強い水流、または危険領域が追いかけてくる
- 危険領域より一定距離下へ沈むとゲームオーバー
- 高度が上がるにつれて危険領域の上昇速度が少しずつ速くなる
- 一定高度ごとに背景、水流、プランクトン構成を変える
- 到達高度とプランクトン得点を記録する
- Time Attack と Endless の BestScore を別々に保存する

#### Endless でブーストを使う意味

- 追いかけてくる危険領域から距離を取る
- 強い下降水流から脱出する
- 離れた高得点プランクトンを狙う
- ルート選択の失敗を立て直す

#### ゲームオーバー時の得点

Time Attack ではゲームオーバー時を0点とする現在のルールを維持する。

Endless ではゲームオーバーが通常の終了方法になるため、到達高度や獲得得点を記録する方式が自然である。必要に応じて、チェックポイントで得点を確定して終了できる仕組みも将来検討する。

#### 実装前に決めること

- 危険領域の見た目と世界観
- 初期速度と難易度上昇の曲線
- 1プレイの想定時間
- 高度とプランクトンをどう得点化するか
- 自分でプレイを終了した場合の記録方法
- ブーストの出現頻度と連続使用の上限

### 4.3 スキン・画面テーマ

現在の柔らかい表現を `Classic`、新しいドット絵表現を `Pixel` として切り替えられる構成を検討する。

#### Pixel テーマの対象

- クラゲ
- プランクトン
- 泡と拍動エフェクト
- 水流
- 背景
- HUD、メニュー、リザルト
- ボタン、アイコン、文字表現

#### スキンの原則

- 見た目だけを変更し、性能や得点条件は変更しない
- Classic と Pixel で同じ当たり判定を使う
- 選択したテーマをブラウザへ保存する
- Canvas の画像補間を無効化し、ドット絵を鮮明に表示する
- スプライトの見た目とゲーム内の論理サイズを分離する
- 使用素材の権利とライセンスを明確にする

## 5. 段階的なロードマップ

### Phase 0: 現在のゲームを安定させる

- スマートフォンとPCの得点バランスを調整する
- スマートフォンの傾き操作をHTTPS環境で確認する
- レイアウト、音量設定、一時停止、リザルトを安定させる
- Time Attack のクリア率と得点分布を確認する

### Phase 1: プランクトンの種類を1つ追加する

- 種類ごとに得点と移動処理を設定できる構造へ整理する
- Swift または Evasive のどちらか1種類を試験追加する
- 出現率と得点をプレイテストする
- 既存の Normal だけでも遊べるバランスを維持する

### Phase 2: Endless の小規模プロトタイプ

- 別モードとして選択できるようにする
- 危険領域によるゲームオーバー条件を試す
- 高度に応じた難易度上昇を最低限実装する
- Time Attack とは別のスコア記録を用意する

### Phase 3: Endless のコンテンツを増やす

- 高度帯ごとの水流や背景変化
- Endless 向けプランクトン
- Jet などの移動補助
- 難易度曲線とプレイ時間の調整

### Phase 4: Pixel テーマ

- Classic と描画処理を分離する
- クラゲと基本プランクトンからドット絵化する
- HUDとリザルトをPixelテーマへ対応する
- テーマ切り替えと保存を追加する

## 6. アップデートを判断する目安

アクセス数だけではなく、次の状態を見て次の更新を判断する。

- 繰り返し遊ぶプレイヤーが増えている
- クリア率や平均スコアが安定している
- 上位スコアが伸びにくくなり、新しい攻略要素が必要になっている
- 新しいモードや見た目を求める反応がある
- 不具合対応より新要素へ時間を使える状態になっている
- 制作者が無理なく更新を継続できる

## 7. Analytics の利用方針

Analytics は、追加要素の判断に必要な最小限の情報だけを取得する。

現在のイベントを維持し、将来必要になった場合は、1プレイ終了時の集計情報を追加する。プランクトン取得ごとに大量のイベントを送ることは避ける。

将来検討する集計項目:

- 選択モード
- クリアまたはゲームオーバー
- プレイ時間
- 到達高度
- 最終得点
- 取得したプランクトンの種類別個数
- 選択テーマ

## 8. ビジネス面での原則

- プレイ中に広告を表示しない
- 広告を設置する場合はホームまたはリザルトへ限定する
- 有料要素を検討する場合も、スキンなどゲーム性能へ影響しないものを優先する
- 得点や操作性能を購入できる仕組みは導入しない
- 更新頻度を義務化せず、個人制作として継続できる範囲を守る
- 人気が出た場合も、既存プレイヤーが遊んでいるルールを急に変えない

## 9. 技術面で将来分離したいもの

実装時に大きく作り直さないため、必要になった段階で次の責務を少しずつ分離する。

- `GameMode`: 制限時間、ゴール、ゲームオーバー、得点計算
- `PlanktonDefinition`: 種類、得点、速度、出現率、行動
- `Theme`: Classic／Pixel の描画とUI設定
- モード別BestScore
- バージョン付きのローカル保存設定

この整理は先に全面実施せず、新機能を追加する直前に必要な範囲だけ行う。

## 10. 現時点の優先順位

1. 現在のスマートフォン得点補正を実機で確認する
2. Time Attack を安定させる
3. プレイヤーの反応とプレイ結果を蓄積する
4. 最初の追加プランクトンを選ぶ
5. Endless の終了条件と難易度曲線を設計する
6. Pixel テーマのビジュアル方針を作る

- Endless の1プレイを何分程度に想定するか
- Endless で途中終了したスコアを記録するか
- Pixel テーマを無料更新、解除要素、将来の有料要素のどれにするか
- スキンをクラゲだけにするか、画面全体のテーマにするか
